# AsciiDoc Feature Gap Analysis

A living catalog of AsciiDoc language features compared against our parser's
current support. Organized by risk — what happens if we encounter the feature in
a real document.

**Source:** the
[AsciiDoc pre-spec PDF export](https://docs.asciidoctor.org/asciidoc/latest/_exports/asciidoc-pre-spec.pdf)
of the [AsciiDoc Language docs](https://docs.asciidoctor.org/asciidoc/latest/)
(492 pages) and the
[Asciidoctor docs](https://docs.asciidoctor.org/asciidoc/latest/syntax-quick-reference/).
The `p.NNN` spec refs below are the PDF's printed page numbers (PDF page =
printed page + 17). A local copy lives at `docs/asciidoc-pre-spec.pdf`
(gitignored) — re-download it from the export URL if missing. The export is a
rolling snapshot, so page numbers can drift as the upstream docs change.

**Status key:**

- **Supported** — implemented and tested
- **Planned** — has a task in the
  [implementation plan](plans/2026-02-20-prettier-plugin-asciidoc.md)
- **Implicit** — works via existing generic mechanisms (verified or
  high-confidence)
- **Unsupported** — not handled; needs work
- **N/A** — not relevant for a formatter

Last updated: 2026-08-18

**Note:** this analysis is a hand-audit against the pre-spec PDF. Task 31
([#7](https://github.com/oxidecomputer/prettier-plugin-asciidoc/issues/7))
proposes deriving a differential conformance suite from the Asciidoctor test
corpus so rows here are backed by (and discovered from) executable cases.

## Tier 1: Would corrupt or mangle output

Features where encountering them in a real document would produce broken
formatting — structural misparse, lost content, or garbled output.

| Feature                               | Spec ref    | Status      | Task     | Failure mode                                                                                                                                                                                                                                                                                                                                                                                                |
| ------------------------------------- | ----------- | ----------- | -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tables                                | p.269–331   | Planned     | Task 18  | `\|===` delimiters and `\|` cell separators unrecognized. Table content treated as paragraphs. 63 pages of spec coverage — by far the most complex feature.                                                                                                                                                                                                                                                 |
| Description lists                     | p.167–175   | Planned     | Task 17  | `Term:: Definition` syntax unrecognized. Terms and definitions treated as paragraph text.                                                                                                                                                                                                                                                                                                                   |
| Bibliography anchors                  | p.115–117   | Planned     | Task 15b | `InlineAnchor` (`[[…]]`) matches the first two of the three brackets, producing an anchor whose id starts with `[` plus a stray `]` text token (`BlockAttributeList` is not involved — its `(?!\[)` lookahead rejects `[[`). The one-arg form `[[[gof]]]` round-trips only by luck; the two-arg form is rewritten: `[[[gof,1]]]` → `[[[gof, 1]]]` (anchor comma-space normalization fires on the misparse). |
| Document header author/revision lines | p.76, 82–87 | Planned     | Task 30  | A blank line is inserted between `= Title` and the author line, detaching it from the header — the author line (and revision line) become body paragraphs and the document loses its metadata. With both present, reflow additionally merges them into one paragraph (`Jane Doe v1.0, 2024-01-15: Remark`). The header join logic only keeps attribute entries contiguous with the title.                   |
| Attribute entry line continuation     | p.33        | Unsupported | —        | The `AttributeEntry` token is single-line, so `:attr: value \` keeps the trailing `\` but a blank line is inserted after it and the continuation line becomes a separate visible paragraph — the attribute value is truncated and the continuation leaks into body text.                                                                                                                                    |
| Literal monospace passthrough         | p.135       | Unsupported | —        | `` `+literal+` `` with plain content round-trips, but content containing formatting characters corrupts: `` `+*not bold*+` `` → `` `\+*not bold*\+` `` — both passthrough marks get escaped, changing rendered output. The `+…+` passthrough is not parsed as a unit, so its `+` marks are exposed to the reflow escape logic.                                                                              |
| YAML front matter                     | p.70        | Unsupported | —        | `---` delimiters and the metadata between them reflow into a single garbled paragraph: `---\nlayout: post\n---` → `--- layout: post ---`.                                                                                                                                                                                                                                                                   |
| Inline STEM macro                     | p.332–337   | Unsupported | —        | `stem:[expression]` not in the inline macro pattern; treated as plain text. Simple expressions survive reflow, but the macro gets none of the atomic-token protection real macros have: reflow can wrap inside the attrlist, and formatting characters in the expression (`**`, `##`, `__`) can be reinterpreted as inline marks.                                                                           |
| Email autolinks                       | p.178       | Unsupported | —        | Bare `user@example.com` not recognized. Treated as plain text. Only `mailto:user@example.com[text]` works.                                                                                                                                                                                                                                                                                                  |

## Tier 2: Would lose structure but preserve text

Features that degrade to plain paragraph text. The content survives formatting
but its semantic structure is lost. Documents remain readable but the formatter
doesn't understand these constructs.

| Feature                                     | Spec ref  | Status      | Task                                                                     | Failure mode                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------------------- | --------- | ----------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Superscript / subscript                     | p.141     | Planned     | Task 24                                                                  | `^super^` and `~sub~` treated as plain text.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Character references                        | p.138–141 | Planned     | Task 24                                                                  | `(C)`, `(R)`, `(TM)`, `--` (em dash), `...` (ellipsis), `->`, `=>` not recognized as replacements.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| Index terms                                 | p.117–119 | Planned     | Task 24b                                                                 | `((term))` and `(((term)))` treated as parenthesized text.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| Underline-style headings                    | p.53–74   | Planned     | Task 28                                                                  | Two-line headings not recognized. Title line treated as paragraph; underline may conflict with block delimiters.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Explicit ordered list markers               | p.156–157 | Planned     | Task 29                                                                  | `1.`, `a.`, `i)` etc. not recognized as list markers. Treated as paragraph text.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| List continuation                           | p.159–166 | Planned     | Task 23                                                                  | Partially implemented: `+` followed by paragraph or indented-literal content attaches to the item, dangling `+` markers are preserved, and `+` directly before a delimited/parent block attaches the block via a post-parse sibling pass (issue #6) — including `+`-chained paragraphs and blocks after it. Remaining gaps: `+` followed by block METADATA (`[source]` etc.) before the block still takes the dangling-`+` path (metadata would need to share one `+` with its block in the printer); a plain (markerless) paragraph directly adjacent after an attached block stays INSIDE the item in Asciidoctor but is detached by the printed blank line (rendering change, predates issue #6); runs of 3+ consecutive `+` marker lines render differently after formatting — the shared quirk model (`src/parse/continuation-markers.ts`) clears the content exemption after one line, and both splitters diverge from Asciidoctor identically; and attaching to ancestor lists / compound open-block wrappers is unsupported. |
| Markdown-style blockquotes                  | p.246     | Unsupported | —                                                                        | `> a` / `> b` lines are merged by reflow into one line, embedding stray mid-text `>` characters (`> a > b`); no blockquote structure is created.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Paragraph-interrupting `+` line             | p.159     | Planned     | Task 23                                                                  | A lone `+` line inside a plain (non-list) paragraph terminates the paragraph in Asciidoctor (two paragraphs, the second starting with `+`); we reflow it into one merged paragraph with a mid-text `+`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Indented continuation before a sibling item | p.150–158 | Unsupported | [#4](https://github.com/oxidecomputer/prettier-plugin-asciidoc/issues/4) | `* a` / `␣␣cont` / `* b`: after an indented continuation line, the item rule only consumes the line-ending newline when more continuation content follows, so a following sibling marker ends the LIST in our AST — one list parses as two, and formatting inserts a blank line between the items. Rendering is preserved (Asciidoctor still produces a single list, nesting included; verified), but the churn and the wrong internal structure are latent hazards for any future list-level feature.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Markdown-style thematic breaks              | p.128     | Unsupported | —                                                                        | `---`, `***`, `___` all treated as paragraph text. (AsciiDoc-native `'''` works fine.)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Smart quotes                                | p.138–139 | Unsupported | —                                                                        | ``"`text`"`` and ``'`text`'`` — the backtick-quote combination likely works (backtick boundary handling prevents misparse) but untested. Curly quote output depends on Asciidoctor, not us.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Horizontal description list                 | p.170     | Unsupported | —                                                                        | `[horizontal]` attribute on description lists. Requires Task 17 (description lists) first; the attribute itself would be preserved but the list wouldn't be recognized.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Q&A lists                                   | p.171     | Unsupported | —                                                                        | `[qanda]` style on description lists. Same dependency on Task 17.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| Description list `;` marker                 | p.172–174 | Unsupported | —                                                                        | Semicolon-terminated terms (`Term;; Description`). Not mentioned in Task 17.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |

## Tier 3: Already works

Features that already work — either explicitly implemented and tested
(Supported) or falling out of existing generic mechanisms (Implicit). Every row
in this tier was verified empirically with a round-trip formatting probe on
2026-08-18 (format once, format twice, compare bytes and idempotency), not just
by code inspection.

| Feature                  | Spec ref    | Status    | Mechanism                                                                                                                                                                                                                                                                                                                   |
| ------------------------ | ----------- | --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Footnote macros          | p.199–201   | Supported | `footnote:` and `footnoteref:` explicitly in `InlineMacro` pattern. Tested.                                                                                                                                                                                                                                                 |
| Keyboard macro           | p.232–233   | Supported | `kbd:` explicitly in `InlineMacro` pattern. Tested.                                                                                                                                                                                                                                                                         |
| Button macro             | p.234       | Supported | `btn:` explicitly in `InlineMacro` pattern. Tested.                                                                                                                                                                                                                                                                         |
| Menu macro               | p.234–235   | Supported | `menu:` explicitly in `InlineMacro` pattern. Tested.                                                                                                                                                                                                                                                                        |
| Icon macro               | p.228–231   | Implicit  | NOT in the `InlineMacro` whitelist — `icon:heart[]` survives only as plain text through reflow (verified by the round-trip probe, including formatting characters in the attrlist), with none of the atomic-token protection real macros get. | Collapsible blocks       | p.340–341   | Implicit  | `[%collapsible]` matches `BlockAttributeList` pattern. needed — these are handled by Asciidoctor at render time, and we preserve the
source syntax that triggers them.

| Source highlighting          | p.251–258 | `:source-highlighter:` attribute + `[source,lang]`. We preserve both.                       |
| Callout icons                | p.268     | Icon rendering for callout numbers. We preserve the `<N>` markers.                          |
| Image positioning / framing  | p.208–210 | `[.float-right]`, `[.thumb]` etc. Just roles/attributes we preserve.                        |
| Image sizing                 | p.211–215 | `width`, `height`, `pdfwidth`, `scaledwidth`. Macro attributes we preserve.                 |
| SVG options                  | p.216–217 | `[%interactive]`, `[%inline]`. Block options we preserve.                                   |
| Table borders / frame / grid | p.314–318 | `[frame=none]`, `[grid=rows]`. Table attributes — will need to preserve when Task 18 lands. |
| Table striping               | p.318–320 | `[stripes=even]`, `:table-stripes:`. Attributes we preserve.                                |
| Table orientation            | p.320     | `[%rotate]`. Block option we preserve.                                                      |
| TOC attributes               | p.346–355 | `:toc:`, `:toclevels:`, `:toc-title:`. Document attributes we preserve.                     |

| Equation numbering           | p.336–337 | Rendering concern for STEM blocks.                                                          |

## Summary

| Tier                    | Count | Action needed                                         |
| ----------------------- | ----- | ----------------------------------------------------- |
| 1: Would corrupt output | 9     | 4 planned, 5 need tasks                               |
| 2: Would lose structure | 14    | 7 planned, 7 need tasks or are blocked on other tasks |
| 3: Already works        | 15    | None — verified empirically 2026-08-18                |
| 4: Rendering only       | 13    | None                                                  |

### Features needing new tasks

These are not yet in the implementation plan:

1. **Inline STEM and icon macros** — add `stem:` and `icon:` to the
   `InlineMacro` pattern (trivial, ~5 min fix; icon currently survives only as
   unprotected plain text)
2. **Email autolinks** — add email pattern to inline URL recognition
3. **YAML front matter** — recognize `---` at file start as front matter
   delimiters
4. **Markdown-style blockquotes** — recognize `> ` at line start
5. **Markdown-style thematic breaks** — recognize `---`, `***`, `___`
6. **Description list `;` marker** — semicolon-terminated terms (add to Task 17)
7. **Horizontal / Q&A description list styles** — blocked on Task 17
8. **Attribute entry line continuation** — extend the `AttributeEntry` token
   across ` \`-continued lines
9. **Literal monospace passthrough** — parse `+…+` (and `` `+…+` ``) as a unit
   so its `+` marks are not exposed to reflow escaping
10. **Indented continuation before a sibling item** — make the list-item rule
    consume the newline after a trailing indented line so a following sibling
    marker continues the same list (filed as
    [#4](https://github.com/oxidecomputer/prettier-plugin-asciidoc/issues/4))

### Known depth gaps in planned tasks

These tasks exist but the spec reveals more complexity than currently scoped:

- **Task 18 (Tables)**: The spec dedicates 63 pages to tables. Features not yet
  in the task: duplicate cells (`3*|`), custom delimiters, TSV format, autowidth
  columns (`[%autowidth]`), table borders/frame/grid attributes, striping,
  orientation, nested tables (`!===`). Consider splitting into sub-tasks.
- **Task 17 (Description lists)**: Missing horizontal layout, Q&A style,
  semicolon marker variant, and description lists with complex continuation
  content.
- **Task 23 (List continuation)**: Spec covers attaching blocks to ancestor
  lists (not just the immediate item), dropping principal text from list items,
  using open blocks as compound wrappers, and a lone `+` line interrupting a
  plain (non-list) paragraph.
