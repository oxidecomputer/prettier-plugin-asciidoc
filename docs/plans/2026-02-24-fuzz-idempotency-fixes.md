# Fuzz Idempotency Fixes

Formatting must be idempotent: `format(format(x)) === format(x)` for all
valid inputs. A fuzz campaign (1000 runs, 100% failure rate, 538 distinct diff
patterns, 884 unique counterexamples) reveals that it currently is not.

The 538 surface patterns reduce to **4 root causes**. Fixing these 4 bugs
should eliminate all observed failures.

## Root Causes

### RC1: Whitespace normalization is not convergent

**Estimated coverage:** ~50% of failures (line-wrapping-collapsed,
line-wrapping-expanded, whitespace-only-change)

**Mechanism:** The printer normalizes whitespace in two places that don't
reach a fixed point in one pass:

1. **Inter-word whitespace.** `fill()` in `src/printer.ts` collapses all
   whitespace (including newlines) to single spaces, then wraps to print
   width.
2. **Intra-construct whitespace.** Spaces inside attribute shorthands
   (`[.  aaa  ]` → `[. aaa]`), xref targets, and macro arguments are
   independently collapsed.

On pass 1, multi-space runs and odd whitespace in the input get normalized,
changing token widths. On pass 2, the already-normalized text has different
widths, so `fill()` wraps at different positions.

**Minimal reproductions:**

_Sub-mechanism A — line-wrap collapse (fill changes wrap point):_

```
". item\nsee https://a[.example.com for info\ntext {a} here\ninclude::a/-./   [
```

Pass 1 wraps the paragraph across two lines. Pass 2 sees the normalized
text, fits it on one line, and inserts a blank line before the block macro.

_Sub-mechanism B — intra-construct whitespace (same wrapping, different
spacing within a line):_

```
"<1> item\n[.aa-a-
```

Pass 1: `<1> item [.aa-a-         ]#$ $ $ $# [.  a-          ]#! $# [.a---a-a-a-  ]#! ! !#`
Pass 2: `<1> item [.aa-a-         ]#$ $ $ $# [.  a-          ]#! $# [.a---a-a-a- ]#! ! !#`

The trailing space inside `[.a---a-a-a-  ]` is collapsed to
`[.a---a-a-a- ]`, shifting the `#` by one character. Same line breaks,
different intra-construct spacing. This is the whitespace-only-change
mechanism (20.2% of failures) — distinct from line-wrap changes.

**Fix direction:** Make all intra-construct normalization happen in the AST
builder (or at least before the printer measures widths), so that the input
to `fill()` is already a fixed point. Specifically:

- Collapse whitespace in attribute shorthand values, xref targets, and
  macro arguments during AST construction, not during printing.
- Ensure `wordsToFillParts()` in `src/reflow.ts` receives text that is
  already fully normalized.
- Verify with: `format(format(x)) === format(x)` for inputs with
  multi-space runs in these constructs.

### RC2: Missing blank line separators between blocks

> **Cross-reference:** This is the same underlying bug as **RC4 (Block
> separation changes)** in `2026-02-24-fuzz-html-preservation-fixes.md`.
> The idempotency test sees it as pass 2 inserting a blank line that
> pass 1 omitted; the HTML test sees the inserted/missing blank line
> changing Asciidoctor's block parsing. Both point to `joinBlocks()`.
>
> Sub-mechanism A (backtick → `[source] + ----`) also overlaps with
> **HTML RC1 (backtick fence → native listing conversion)**. Fixing
> the backtick conversion would eliminate this sub-mechanism entirely.

**Estimated coverage:** ~45% of failures (blank-line-inserted-\*,
blank-line-near-\*, blank-line-moved)

**Mechanism:** When a paragraph is followed by a block delimiter (`----`,
`====`, `....`, `////`, `++++`, `____`, `****`) or a block macro
(`include::`, `image::`, `ifdef::`, `endif::`), the printer doesn't always
emit the required blank line separator. Pass 1 produces valid but
tightly-packed AsciiDoc. On re-parse, the parser correctly separates the
elements. Pass 2 then adds the missing blank line.

This is generic across **all 8 block delimiter types** plus block macros.
The `joinBlocks()` function in `src/print-join.ts` handles block
separation, but certain combinations — especially paragraph → block
metadata → delimiter — aren't getting the right separators.

**Minimal reproductions:**

_Sub-mechanism A — `[source,lang]` + `----` gap (Pattern 1, 419
occurrences):_

````
see https://![a.example.com for info
```rust
a \* b
````

Pass 1 converts backtick fence to `[source,rust]` + `----`. Pass 2 inserts
a blank line between `[source,rust]` and `----`.

_Sub-mechanism B — paragraph → generic block delimiter (Pattern 8):_

```
". item\n [ \n====\n[.a
```

```diff
  . item [

  ====
- [.a]#x#
+ [.a]#x#
+
+ ====
  ====
```

The `====` example block delimiter gets a blank line inserted after the
paragraph content inside it. This exercises a different delimiter type than
the listing-block-specific sub-mechanism A.

_Sub-mechanism C — paragraph → block macro (Pattern 40):_

```
"- item\nsee https://![a.example.com for info\nsome ##x## text\ntext {A } here\nendif::[
```

```diff
- * item see
-   https://![a.example.com for info
- some ##x## text
- text {A } here
+ * item see https://![a.example.com for info some ##x## text text {A } here
+
  endif::[]
```

The paragraph content collapses to one line (RC1 overlap) and a blank line
appears before `endif::[]`. Block macros are a different code path from
block delimiters in `joinBlocks()`.

_Sub-mechanism D — leading whitespace → blank line removal (Pattern 4):_

```
 \nNOTE: text
```

(Leading space on the first line, then newline, then `NOTE: text`.)

```diff
-
-
  NOTE: text
```

Pass 1 produces two blank lines before `NOTE: text`. Pass 2 removes them.
The leading-whitespace line creates a paragraph that formats as blank lines,
which are then collapsed on re-format. This is the only sub-mechanism where
blank lines are _removed_ rather than _inserted_.

**Fix direction:** Audit `joinBlocks()` in `src/print-join.ts`. The rule:
any block followed by a different block type always gets a blank line, with
narrow exceptions only for stacking metadata (attribute lists, block titles,
anchors) onto the block they annotate. Make sure:

- The stacking exceptions never produce output that re-parses differently.
- Backtick → `[source] + ----` conversion emits the attribute list and
  delimiter with no blank line between them (they're metadata + block, not
  two separate blocks).
- Block macros (`include::`, `image::`, etc.) are treated as block
  boundaries that require a preceding blank line.

### RC3: `fill()` breaks inside atomic inline constructs

**Estimated coverage:** ~15% of failures (overlaps significantly with RC1)

**Mechanism:** The parser has several inline tokens whose regexes forbid
newlines:

- **Xref shorthand** `<<<id, label>>>` — regex `<<[^>\n]+>>` rejects `\n`
- **Inline URL** `https://url[text]` — regex `[^\s[\]]+` rejects whitespace
  before `[`
- **Inline macro** `mailto:addr[text]` — regex `:[^\s[]*\[` rejects space
  between `:` and `[`

When `fill()` inserts a line break inside one of these constructs, the
formatted output no longer matches the token regex on re-parse. The token
is reinterpreted as something else entirely:

- `<<<id,\nlabel>>>` → `<<<` on its own line becomes a bibliography anchor
  context, `label>>>` becomes text.
- `https://url\n[text]` → URL loses its attribute list, `[text]` becomes a
  standalone attribute list.

The printer's `dangerousAtLineStart` mechanism in `src/reflow.ts` protects
against block-level syntax appearing after a line break, but doesn't protect
these inline constructs.

**Minimal reproduction:**

```
some ##! ! ! ! !!## text see <<<   aa-a-a-aa >>
```

Pass 1 wraps the `<<<` to a new line. Pass 2 sees `<<<` at line start
(parsed as bibliography anchor start) and produces a blank line + different
structure.

**Fix direction:** In the printer, make these inline constructs
non-breakable. Options:

- Wrap `<<<...>>>`, inline URLs with `[...]`, and inline macros in
  Prettier's `group()` so `fill()` treats them as atomic units.
- Alternatively, add them to the "dangerous at line start/end" mechanism
  in `src/reflow.ts` so that `fill()` never breaks immediately before
  `<<<` or inside a URL's `[...]`.

### RC4: Content-altering formatting

**Estimated coverage:** ~5% of failures (content-changed,
content-changed-expansion, complex-content-change)

**Mechanism:** The printer changes semantic content in a few cases:

1. **Empty `[]` stripped from URLs.** `https://a.example.com[]` becomes
   `https://a.example.com`. These are semantically different: `[]` marks
   an explicit macro invocation (the URL is a clickable link with
   auto-generated text), while a bare URL may be parsed differently
   depending on what follows.

2. **Whitespace inside macro arguments altered.** Extra spaces in
   `link:`, `xref:`, and `mailto:` arguments get collapsed when they
   shouldn't be (the content inside `[...]` is opaque to formatting).

3. **Constructs re-interpreted.** In some cases, reformatted output is
   valid AsciiDoc but represents a different parse tree than the original.

**Minimal reproduction (Pattern 3, 5 occurrences):**

```
see https://a.example.com[
```

Pass 1: `see https://a.example.com[] here`
Pass 2: `see https://a.example.com here` (brackets stripped)

**Fix direction:**

- Preserve `[]` on inline URLs and macros — never strip empty attribute
  lists.
- Treat content inside `[...]` on macros as opaque: don't collapse
  whitespace within macro argument lists.
- Add idempotency-focused tests for each inline macro type with empty and
  whitespace-heavy attribute lists.

## Attack Order

| Priority | Root Cause                    | Rationale                                                                                              |
| -------- | ----------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1        | RC2: Block separators         | Most mechanical, self-contained fix. Targets `joinBlocks()` in one file. ~45% of failures.             |
| 2        | RC1: Whitespace convergence   | Highest-value but hardest. Touches how `fill()` interacts with inline node printing. ~50% of failures. |
| 3        | RC3: Atomic inline constructs | Surgical change to printer. Mark specific constructs as non-breakable. ~15% of failures.               |
| 4        | RC4: Content alteration       | Small, targeted fixes. Preserve `[]`, don't mangle macro arguments. ~5% of failures.                   |

Many failures are caused by multiple root causes simultaneously (e.g., a
URL in a paragraph that gets both wrongly wrapped AND loses its blank line
separator). The coverage percentages overlap. But the hitting-set property
holds: every one of the 538 distinct diff patterns is explained by at
least one of these 4 root causes.

## Verification

After each fix, re-run the fuzzer (`bun run fuzz`) and compare failure
counts against this baseline:

- **Baseline:** 1000/1000 failures, 538 distinct patterns
- **After RC2:** Expect blank-line-inserted-\* categories to drop sharply
- **After RC1:** Expect line-wrapping-\* and whitespace-only-change to drop
- **After RC3:** Expect xref-or-anchor and remaining URL patterns to drop
- **After RC4:** Expect content-changed-\* to reach zero

Target: 0/1000 failures.
